THE GOAL
--------
Crate has a custom scripting language "cScript" for gameplay logic, currently
executed by a hand-rolled tree-walking interpreter (src/script/Interpreter.cpp)
over an AST from a hand-rolled lexer + recursive-descent parser
(src/script/Lexer.*, src/script/Parser.*, src/script/Ast.h). Users will keep
writing cScript exactly as today. The change: at some point scripts get
compiled to real native C++, and that compiled code — not the interpreter —
executes during Play mode / at runtime. The interpreter itself is NOT being
removed: it stays exactly as-is and continues to power everything that happens
while Play is stopped (Script Editor, autocomplete, Inspector default-value
editing). Only actual gameplay hook execution (start/update/physicsUpdate)
switches to compiled native code, and only while Play is running.

Hard requirement from the user: "make sure everything works exactly as it does
now." Treat any behavior change as something that needs explicit, separate
sign-off — do not casually "fix" things you notice along the way.

DECISIONS ALREADY MADE — DO NOT RE-LITIGATE THESE
---------------------------------------------------
1. Namespace = a property set ON THE SCRIPT ASSET ITSELF, editable via the
   Inspector when a script asset is selected in the Asset Browser. It is NOT a
   cScript language keyword and NOT inferred from folder structure. Defaults
   to "Global" when unset. All scripts sharing the same namespace value
   compile together into one `<namespace>.dll`.

2. Compilation happens ONLY when the user presses Play. Never per-keystroke,
   never per-individual-save. Exact required flow:
   - On Play press: force-save all unsaved scripts (reuse the existing
     ScriptEditor::saveAll()).
   - Compute which namespaces are dirty (source changed since last successful
     build) and rebuild them (see Phase 3 for the dependency-graph nuance).
   - If ANY namespace fails to compile: Play does not start at all. Log which
     script/namespace failed and the compiler's diagnostic text via the
     EXISTING Engine Console (src/editor/Console.h — use
     `Console::get().error(Console::Channel::Engine, "<message>")` or the
     `CR_ERROR("script", "<message>")` macro from src/core/Log.h, which
     already routes to the same place). Do NOT build a new console UI — one
     already exists and is wired into an "Engine Console" panel.
   - While Play IS running: the Script Editor must refuse to save or trigger
     any recompilation at all (block saveCurrent()/saveAll()/pushToSystem()
     while playing; grey out the Save button / show a status message).

3. The Inspector must keep showing AND letting you edit a running script's
   live field values while Play is active, exactly as it does today, even
   though the code executing is now compiled native code instead of
   interpreted. The user explicitly chose this over the cheaper alternative
   (read-only/hidden fields during Play), accepting that it requires the code
   generator to also emit a per-class reflection/accessor table.

4. Vector2/Vector3 aliasing is PRESERVED exactly as today. Today they are
   reference-counted ScriptObjects (shared_ptr), so `var b = a;` between two
   vectors aliases them (mutating b.x also mutates a.x) — this is arguably an
   unintentional quirk, but no script or test relies on fixing it, and the
   user explicitly chose to preserve it as-is for this task. Do NOT change
   vector semantics to true value types as part of this work. That is
   explicitly deferred to a separate, future task if ever revisited.

ARCHITECTURE, ONE PARAGRAPH
----------------------------
Keep the entire existing interpreter stack (Interpreter, ScriptSystem,
ScriptComponent, Value/ScriptObject) completely UNCHANGED as the edit-time
engine. Add a second, parallel execution backend that only takes over
start()/update(dt)/physicsUpdate(dt) while Play is active: cScript's AST is
translated to real C++ (reusing the interpreter's own helper semantics,
extracted into a stateless shared Runtime library so behavior transfers
mechanically instead of being independently re-derived), compiled+linked
per-namespace into a versioned DLL via the same MSVC toolchain
scripts/build.ps1 already uses, and loaded via a narrow extern "C" factory
ABI. A generated per-class reflection table (field get/set function pointers,
method invoke, an overflow map for dynamically-created fields) serves THREE
needs at once with one mechanism: Inspector-during-Play sync, the
get_component/signals/this.base dynamic-dispatch surface, and cScript's
undeclared-field auto-creation behavior (`some_undeclared_name = 5;` silently
creating a new field — see Interpreter.cpp's lvalue(), ~line 931-954).

KEY FACTS DISCOVERED DURING INVESTIGATION (verified against the actual repo,
not assumed — re-verify line numbers if files have moved since this was written)
--------------------------------------------------------------------------------
- crate_core is a single STATIC library (CMakeLists.txt) linked into Crate.exe
  and all eight *_tests.exe targets. There is ZERO existing DLL / plugin /
  LoadLibrary / subprocess-compiler infrastructure anywhere in this codebase.
  A DLL boundary must be built from scratch. Crate.exe cannot patch its own
  already-loaded static code, so the DLL boundary is mandatory, not optional.
- scripts/build.ps1 is the canonical build entry point:
  `powershell -ExecutionPolicy Bypass -File scripts\build.ps1 [Debug|Release]`
  It locates VS via `vswhere.exe -latest -property installationPath`, then
  runs everything as ONE `cmd.exe /c "<vcvars64.bat> && <cmake config> && <cmake --build>"`
  invocation, because vcvars64.bat's INCLUDE/LIB/PATH env vars don't survive
  across separate process launches. Debug builds into build/, other configs
  into build-<Config>/ (e.g. build-Release/).
- Compiler flags actually in use (read directly from build/build.ninja and
  build-Release/build.ninja, do not assume):
    Debug:   /DWIN32 /D_WINDOWS /EHsc /Zi /Ob0 /Od /RTC1 -std:c++17 -MDd
    Release: /DWIN32 /D_WINDOWS /EHsc /O2 /Ob2 /DNDEBUG -std:c++17 -MD
    crate_core additionally uses /W4 /permissive-
    Include dirs: -I<repo>\src -I<repo>\third_party
  CRT linkage (/MDd vs /MD) MUST match between the running host exe and every
  generated script DLL, or you get heap-mismatch crashes the instant a
  std::string/shared_ptr/std::function crosses the DLL boundary. There is no
  CMAKE_MSVC_RUNTIME_LIBRARY override in CMakeLists.txt — it's whatever CMake's
  per-config MSVC default is for Debug vs Release.
- The Inspector's script reflection today (src/script/ScriptComponent.cpp,
  drawInspector() ~line 180-224): iterates `obj_->fields` (an
  unordered_map<string, Value> on ScriptObject, src/script/Value.h ~line 80-98)
  and cross-references cls_->decl->fields (the AST's FieldDecl list,
  src/script/Ast.h ~line 96-100) purely for the declared-type string. Editing
  an Int/Float/Bool widget mutates the live Value in place by reference — no
  setter/dispatch layer. drawRefField() (ScriptComponent.cpp ~115-178, added
  for the actor/component reference picker feature) generalizes this further
  for Actor/component-typed fields via ctx_->getComponent(actor, declType),
  which is itself generic over any type name (works for native components
  like Camera/Fog and for other script classes uniformly).
- ScriptSystem::compile() (ScriptSystem.cpp ~84-142) is the whole "compile"
  story today: lex -> parse -> if the class name already exists in types_,
  REUSE the same ClassInfo* and just swap its ->decl (new AST) and bump
  ->generation. ClassInfo* pointer identity is stable across edits forever —
  this is why hot-reload today is instant and pointer-safe. ScriptComponent::
  ensureObject() (ScriptComponent.cpp ~49-63) checks cls_->generation !=
  objGen_ and, if changed, drops obj_ entirely and rebuilds it fresh from
  Interpreter::instantiate() (re-runs field initializers from scratch — no
  attempt to migrate old field values across a recompile, today or planned).
- KNOWN EXISTING GAP (do not accidentally fix or worsen without flagging it):
  editing a BASE class's source does NOT bump a DERIVED class's own
  ClassInfo::generation (ScriptSystem.cpp ~118 only bumps the recompiled
  class's own slot) — so a live derived-class ScriptComponent today silently
  keeps running on stale base-class behavior until something else touches it.
  This existing bug becomes a much more dangerous ABI/layout mismatch once
  compiled — see Phase 3's cross-namespace dependency graph, which exists
  specifically to prevent this failure mode from becoming a hard crash.
- get_component(type_of(X)), ClassInfo::isA (string-name comparison up the
  base chain, ClassInfo.h ~64-71), this.base.method(), and Callables (signals'
  .connect/.emit) are ALL resolved BY NAME at runtime today, in
  Interpreter.cpp's evalCall and friends — deliberately, because which
  concrete script classes are attached to which Actor is only known at
  scene-authoring/runtime. This dynamic-dispatch requirement does not
  disappear just because the code becomes compiled native C++; the plan's
  reflection table (Phase 5) is what replaces the by-name lookup for compiled
  classes.
- do_async (Interpreter.cpp's runFunction, ~113-184) frame-steps by re-walking
  a function's TOP-LEVEL statement list every call and skipping to the Nth
  top-level do_async, running one loop iteration, then returning; resume state
  lives on ScriptObject::asyncResumeFn/asyncResumeIndex (Value.h ~96-97) — only
  ONE function's suspension survives per object at a time. Critically: a
  do_async NESTED inside an if/switch/another loop is NOT frame-stepped — it
  runs synchronously to completion in one call via the generic execStmt
  dispatch (same as a plain do-while), guarded by a 1,000,000-iteration cap.
  Native codegen must reproduce BOTH behaviors exactly (top-level = state
  machine, nested = synchronous loop) — this nested-vs-top-level distinction
  is easy to miss and is not covered by any existing test, so Phase 6 adds a
  new test specifically for it.
- No scene serialization exists anywhere in this codebase yet (grepped,
  confirmed absent) — script field values are never persisted to disk beyond
  the .cscript source text itself. This means there is no on-disk format this
  work needs to stay compatible with, only the in-memory Inspector contract.
- AssetDatabase (src/assets/AssetDatabase.h/.cpp) is ONLY a path<->UUID map —
  it has no field for arbitrary per-asset metadata. Recommendation (Phase 1):
  do not extend it; add a new small sidecar file mirroring its own tab-
  separated, project-root, gitignored convention instead, keyed by class name
  (not path) since ScriptSystem already thinks in terms of class names.

PHASE 6 — do_async codegen.
  Reconfirmed exact interpreter semantics (Interpreter.cpp ~113-184 and
  execStmt's DoAsync case ~218-234) — reproduce ALL of these exactly:
    - Only TOP-LEVEL do_async statements in a function's own body get frame-
      stepped, one-iteration-per-call treatment.
    - A do_async NESTED inside an if/switch/another loop runs synchronously
      to completion in a single call via the generic execStmt dispatch
      (identical to a plain do-while), guarded by the same 1,000,000-
      iteration cap. This is exactly what ships today — not a hypothetical
      edge case to design around later.
    - Only ONE function's suspension survives per object at a time
      (asyncResumeFn/asyncResumeIndex on ScriptObject) — calling a different
      hook while one is suspended discards the other's resume point.
    - Statements strictly BEFORE the target top-level do_async are NOT re-
      executed on a resumed call — only object fields survive a yield, not
      locals declared before the do_async.
  Codegen strategy (hand-rolled `switch`-based resume-point state machine,
  computed STATICALLY at codegen time since the generator already knows
  exactly which statement index each top-level do_async sits at):
    Value ClassName_Native::call_update(std::vector<Value> args) {
        float dt = ...;
        int resumeAt = (asyncResumeFn_ == "update") ? asyncResumeIndex_ : -1;
        switch (resumeAt < 0 ? 0 : <case for resumeAt>) {
        case 0:
            /* statements before the first top-level do_async */
            [[fallthrough]];
        case <N>:
            if (Runtime::truthy(eval_cond_0())) {
                bool broke = run_body_0_once(); // break/continue map to
                    // plain C++ break/continue inside body_0's own emitted
                    // loop-guard block
                if (!broke) {
                    asyncResumeFn_ = "update"; asyncResumeIndex_ = <N>;
                    return Value::Null_();
                }
            }
            [[fallthrough]];
        /* ... one case per top-level do_async ... */
        }
        if (asyncResumeFn_ == "update") {
            asyncResumeFn_.clear(); asyncResumeIndex_ = -1;
        }
        return Value::Null_();
    }
  Chosen over C++20 coroutines specifically because coroutines' own suspend/
  resume/lifetime rules are a differently-specified feature that risks
  subtly diverging from the interpreter's exact, already-tested behavior —
  the hand-rolled switch gives full, auditable control over matching it
  precisely.
  Modified files: src/script/CodeGen.h/.cpp — the statement-emission pass
    needs to detect a function's own top-level do_async positions and emit
    the switch/fallthrough shape there; everywhere else, ordinary recursive
    emission (including a do_async nested inside a conditional, which

  New test: tests/do_async_native_tests.cpp — port the existing test from

THE UNIFYING DESIGN (read this before touching any code -- almost every
sub-phase below reuses the SAME core mechanism)
-----------------------------------------------------------------------
Add `const CompiledClassInfo* compiledInfo = nullptr;` to ScriptObject
(Value.h), alongside its existing `nativePtr`. This generalizes the
EXISTING "live view onto a native pointer" pattern (today used only for
Fog/Camera BuiltinComponents, matched purely by `builtin` string) to also
cover a native COMPILED SCRIPT instance: when `nativePtr` AND
`compiledInfo` are both set, field/method access goes through
`compiledInfo`'s FieldAccessor/MethodAccessor/overflow tables (Phase 5)
instead of the `fields` map. A ScriptObject is now exactly one of FOUR
kinds, symmetric and uniform:
  1. `cls != nullptr`                          -> interpreted script instance (fields map)
  2. `nativePtr != nullptr, compiledInfo == nullptr, builtin != ""` -> BuiltinComponent live view (Fog/Camera, existing)
  3. `nativePtr != nullptr, compiledInfo != nullptr` -> compiled script instance live view (NEW)
  4. none of the above, `builtin != ""`, cls==nullptr, nativePtr==nullptr -> a plain aggregate (Vector2/Vector3, InputButton -- existing)

New shared free functions (crate_script_runtime -- see below for why
Interpreter.cpp itself moves into crate_script_runtime to make this
possible) dispatch generically over all four kinds:
  Value getObjectMember(const std::shared_ptr<ScriptObject>& obj, const std::string& name, int line);
  bool trySetObjectMember(const std::shared_ptr<ScriptObject>& obj, const std::string& name, const Value& v);
  Value callObjectMethod(ScriptContext* ctx, const std::shared_ptr<ScriptObject>& obj, const std::string& method, std::vector<Value> args, int line);
Kind 1 (interpreted) routes through a REAL `Interpreter(ctx, obj)` --
which is why Interpreter.cpp needs to become buildable inside a script
DLL too (confirmed clean: it only ever touches engine state through
`ctx_`, exactly like Runtime.cpp already does -- no singleton access,
verified by re-reading its full #include list). Kind 2/3 route through
the reflection table (compiledInfo) or the existing getNativeField/
setNativeField Fog/Camera table. This ONE mechanism is what makes
get_component's result usable (call/read on whatever it returns,
regardless of whether the target happens to be interpreted or compiled),
what makes a Callable/signal invokable regardless of its bound target's
kind, and what makes this.base.method() safe (see 9f).

Interpreter.cpp's OWN evalMember/evalCall/assign get a small, surgical
extension: everywhere they currently only handle `obj.obj->cls` (an
interpreted target) for a general object reference, ALSO try the new
compiledInfo path via the shared helpers above. This is not a new
capability for the INTERPRETER conceptually (it already treats
nativePtr-backed Fog/Camera specially) -- it's closing the exact gap the
starting-point bug describes, generalized to any compiled class, not
just Fog/Camera.

9f. this.base.method() + real script-to-script inheritance (HARDEST,
    HIGHEST-RISK sub-phase -- do it LAST, after everything else above is
    solid, so a real setback here doesn't block already-working parity
    elsewhere).
    - CodeGen.cpp: accept ANY other currently-known script class name as
      a valid `base` (not just Actor/Actor2D/Actor3D), REMOVING that
      refusal.
    - CHOSEN APPROACH (per the ALREADY-approved plan's own Phase 3 notes,
      which flagged this exact fork and named real inheritance as the
      PRIMARY design, composition-by-name-lookup only as a documented
      fallback -- re-read that section of this file before starting):
      REAL C++ inheritance across the DLL boundary when base and derived
      live in different namespaces. `class Derived_Native : public
      Base_Native` literally, requiring Derived's namespace to
      `#include` Base's generated header and link against Base's
      generation-versioned import library (.lib). WHY real inheritance
      and not composition: cScript field/method access on `this` compiles
      to DIRECT C++ member access for performance (`this->field_x`, not a
      name-indexed lookup) -- under a composition (no-inheritance) model,
      a base class's method body invoked against an unrelated derived
      instance's memory would be undefined behavior, since there's no
      guaranteed layout compatibility. Real inheritance is the only way
      that stays both fast (direct member access preserved) AND safe.
    - ScriptBuild.cpp: computeRebuildSet() stops being the identity
      function -- build the REAL namespace dependency graph (edge A->B if
      any class in namespace A has ClassInfo::baseClass resolving to a
      class in namespace B, A != B), take the transitive closure over the
      dirty set, and topologically sort so buildNamespace() is called for
      every dependency BEFORE its dependents (a base namespace must exist
      -- built AND its .lib available -- before a derived namespace's
      compile step runs). EditorApp::setPlaying() must build namespaces
      in the returned ORDER, not an unordered set/loop as it does today.
    - buildNamespace() needs new parameters/logic: for a namespace with
      cross-namespace base classes, add `-I<baseNamespaceGenDir>` to the
      cl.exe invocation and the base namespace's `.lib` to the link.exe
      invocation, and the derived class's generated header must
      `#include "<BaseNamespace>/<Base>_Native.gen.h"` and declare `class
      Derived_Native : public crate::script::generated::Base_Native`.
    - `this.base.method()` then compiles to a literal, direct C++ call:
      `this->Base_Native::fn_<method>(args)` (or similar direct-base-call
      syntax) -- genuinely trivial ONCE real inheritance is in place,
      exactly as fast/simple as the interpreter's own base-chain
      findFunction() dispatch, just resolved at compile time instead of
      per-call.
    - Field initialization order (base fields first, then derived, so
      derived overrides win -- matching Interpreter::constructFields()
      exactly) needs care in the generated constructor: call the base
      class's constructor first (via the C++ member-initializer list),
      then apply the DERIVED class's own field initializers only for
      fields it re-declares, exactly mirroring constructFields()'s
      chain-walk-then-overwrite behavior.
    - SAME-NAMESPACE inheritance (base and derived in the same DLL) is
      the easy subset of this -- do it FIRST as a stepping stone before
      attempting cross-namespace, since it needs none of the
      ScriptBuild.cpp dependency-graph work, just CodeGen.cpp emitting
      real inheritance syntax within a single generated .cpp/.gen.h set.
    - Tests: same-namespace inheritance parity test first (simplest);
      then cross-namespace (two namespaces, one deriving from the other,
      exercising ScriptBuild's new dependency-order build); this.base.
      method() parity; a base-class field override parity test;
      confirm computeDirtyNamespaces + the new dependency closure
      correctly rebuilds a DERIVED namespace when only its BASE
      namespace's source changed (this is the exact scenario Phase 3's
      "known existing gap" note about the interpreter warned would become
      a hard crash instead of a benign staleness bug once compiled -- this
      sub-phase is what actually closes that gap for real).
    - IF real cross-DLL inheritance proves too fragile in practice
      (ABI/build issues that can't be resolved with reasonable effort):
      fall back to the plan's documented alternative (composition +
      by-name this.base dispatch through NativeClassRegistry, with EVERY
      field access on `this` within a class that HAS a script base
      rewritten to go through name-based accessors instead of direct
      member access, to stay safe under composition) -- but only after a
      genuine, documented attempt at real inheritance first, and only
      with a clear note here explaining why the fallback was needed.

  KEY DESIGN FINDING BEFORE WRITING ANY CODE (re-reading Interpreter.cpp
  carefully, as planned): resumable (frame-stepped) treatment is NOT a
  property of "this function has a do_async at its own top level" in

  call could reach a function some OTHER way that might also count as

  syntactic "is there a do_async at this function's own top level" one.
  TWO REAL BUGS FOUND AND FIXED WHILE DESIGNING THE do_async STATE MACHINE
  (both PRE-EXISTING in Phase 2's switch/loop codegen, unrelated to
  do_async specifically, but found by tracing through exactly how a
  goto-based resumable body would need to interact with break/continue):
    1. The synchronous-loop codegen (DoWhile / nested DoAsync) placed its
       1,000,000-iteration guard check AFTER the loop body, matching the
       ORIGINAL text but NOT actually matching Interpreter::execStmt's
       real order of operations closely enough: since a native C++
       `continue;` jumps straight to the loop's condition re-check,
       skipping any code between the continue and the closing brace, a
       cscript `continue;` inside such a loop's body was silently
       SKIPPING the guard-check every single time -- an infinite-loop
       safety-net bypass. Fixed by moving the guard check to the TOP of
       the loop body (before user statements), so it unconditionally runs
       exactly once per iteration attempt regardless of how that iteration
       ends.
    2. Interpreter::execStmt's Switch case catches ONLY BreakSignal, never
       ContinueSignal -- meaning a cscript `continue;` written inside a
       switch case, when that switch sits inside a loop, must skip PAST
       the switch entirely and continue the ENCLOSING loop. But Phase 2's
       switch codegen wraps each switch in its own `do { } while(false)`
       specifically so a native `break;` inside a case correctly targets
       just the switch -- and a native C++ `continue;` written inside that
       SAME do-while ALSO targets it (native continue/break always target
       the syntactically nearest loop/switch, with no way to "see through"
       one from the inside) -- so a user's `continue;` inside a switch case
       was incorrectly only exiting the switch's own do-while(false)
       wrapper (behaving like a break) instead of actually continuing the
       real enclosing loop, silently running fewer loop iterations than
       intended and skipping whatever code came after the switch for that
       pass. Fixed by replacing ad hoc native break/continue with two
       explicit FnCtx stacks (breakTargets/continueTargets): every loop
       (native synchronous OR Phase 6's resumable do_async) pushes onto
       BOTH, with continue ALWAYS compiling to a `goto` to a label placed
       at the very end of that loop's own body (reachable through any
       number of nested switches, since a forward goto out of nested
       blocks is legal, ordinary C++); a Switch pushes onto breakTargets
       ONLY (break still native, unchanged, correctly targets the switch),
       deliberately leaving continueTargets exactly as the nearest
       enclosing loop already left it, so continue "sees through" any
       number of intervening switches to whichever loop actually encloses
       them. This also directly supplied the exact break/continue-
       targeting primitive Phase 6's own resumable do_async bodies needed
       (a `goto` to an end-of-body label, with break additionally setting a
       "broke" flag so the yield logic can tell "aborted, don't yield" from
       "continued or fell through normally, DO yield" apart) -- the SAME
       mechanism serves both the bug fix and the new feature.
  New Gen::emitHookBody() (CodeGen.cpp): if a hook function's body has no
  TOP-LEVEL DoAsync statement, behaves identically to block() (Phase 2,
  unchanged). Otherwise emits `int __resumeAt = (asyncResumeFn_ == "<hook>")

  this sub-phase's own parity test, which reads the live accessor, not the

  writes specifically. Not fixed here (would need a bigger design: push-

  hook cycle, a real performance/correctness tradeoff) -- flagged here for
  a future task or an explicit user decision, per the "make it 1:1, no
  exceptions" directive obligating me to surface rather than quietly work

  OPTIONAL: ScriptSystem.cpp's ctx_.getComponent used to build a brand-new

  compiledInfo, owner}` by hand. CompiledClassInfo also grew
